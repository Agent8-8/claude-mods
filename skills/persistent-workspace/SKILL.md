# Persistent workspaces

For Claude Code Desktop on this Mac, help the user keep work in durable local folders without needing to understand paths. This is guidance, not a guarantee that every session starts in a particular folder. Never weaken permissions, change settings, delete, rename, overwrite, move or reorganize existing files or projects as part of workspace setup. Respect a user-specified location or request not to create a folder.

## Decide where to work

- If the current session is already in a real task or project directory, stay there. Continue the same session in the same folder, even after a new topic, unless the user explicitly requests a different project or location. A folder chosen for an existing project is authoritative; never create a duplicate or nest a new workspace within it automatically.
- If working locally in exactly `~/Claude/chats` or in a confirmed Claude Desktop no-folder scratch workspace, and the user asks for work that needs durable files, create one task workspace. This also applies when the conversation began with questions and a later message requests files. Do not create one for a simple question, read-only investigation, or explicitly temporary work.
- For a new substantial, reusable undertaking such as a website, app, game, tool, or ongoing named project, automatically choose a project workspace under `~/Claude/projects` even if the user does not say the word project. An isolated document, small one-off deliverable, experiment, or scratch task belongs under `~/Claude/chats`. When uncertain, use a task workspace rather than asking an unnecessary question. An explicit destination or an existing project takes precedence. Create a project workspace only if it does not conflict with an explicit path or an existing intended project. If the name clearly matches an existing project, use that existing location if unambiguous; if unclear, ask which to use rather than create a duplicate or change folders silently. For a request to continue an existing project from the shared chats folder, invoke this skill first, locate the matching project, and call the Desktop change-directory tool before editing. Use absolute paths during the current turn, since the switch completes after the turn. If the intended project is ambiguous, ask; respect approval prompts. Do not treat a shell `cd` or absolute-path edit as a session switch.
- Do not apply this local setup in cloud, SSH, or Cowork sessions. Never assume an arbitrary directory is scratch. If context is uncertain, preserve the current workspace and explain how to select a folder.

## Create and switch

Use the bundled helper once for each new workspace; pass a short task or project title as one argument, not shell code. For a task run `python3 "${CLAUDE_SKILL_DIR}/create_workspace.py" --kind task --title "short title"`; for a project use `--kind project`. It creates a uniquely named directory under `~/Claude/chats` or `~/Claude/projects`, respectively, without overwriting an existing directory. Use today's local date for tasks. If it fails, explain the issue and don't claim success. Before rerunning, check whether the first invocation already created a folder.

Use a short, recognizable description of the actual work in each new workspace title, preferably 2–5 meaningful words (for example, `2026-11-11-ecc-setup` or `student-dashboard`), rather than a vague name such as `task` or `project`. Give new user-facing files similarly concise, descriptive names, preserving their appropriate extensions. Respect requested filenames, existing project conventions, and required names such as `CLAUDE.md` and `PROJECT.md`; never rename existing files merely to follow this guideline. Do not add separate description files or long sidebar labels.

For newly created standalone user-facing deliverables, include the local date in `YYYY-MM-DD` format along with the short description, for example `2026-11-11-meeting-notes.pdf`. Do not date source code, configuration, required filenames, project files with established names, or files for which the user requests a specific name. Do not rename existing files. Task folders already receive a date from the helper; do not change existing project folder names or force a date onto them.

Discover and use the desktop `mcp__ccd_directory__change_directory` tool with the returned absolute path. This may require approval; do not bypass or alter permission settings. The working-directory switch completes only at the end of the turn. Until then, use absolute paths inside the new directory for the user's work. If permission is denied or the tool is unavailable, say the folder was created but the session did not switch; offer its path for selection, and don't imply work was saved elsewhere. Confirm the switch on a subsequent turn when relevant; don't claim verification earlier.

Keep each project self-contained: project source and its README belong in the project folder; create subfolders only when the task calls for them, not an elaborate empty template. For a general task, keep its input copies, working files, and deliverables in its own task folder when useful, respecting existing input locations and never moving originals without permission. When a user asks to resume a project from the shared chats folder, check only immediate existing project directory names (no recursive search or reading other project contents) before creating anything, and switch only if the intended project is unambiguous. Create only files required for the user's task. For a substantive new project, a concise README explaining what the project is and how to run it is useful when appropriate; update it when material project facts change. Use Git if the user asks or when appropriate for a coding project, but don't create a GitHub repository, publish, push, change visibility, or expose files without authorization. Local Git is not a backup. Never automatically copy credentials, private app data, or configuration to a backup. Tell the user the folder location briefly when created; do not discuss these mechanics on every response.

## Project sidebar organization

For a confirmed local project rooted in `~/Claude/projects/<project-name>`, organize this session in a collapsible Claude Desktop sidebar section named `Project: <project-name>`. This applies after selecting or creating the project and when opening another session already in that project. It does not apply to general chat, scratch, cloud, SSH, Cowork, arbitrary repositories, or projects outside that directory. Do not move other sessions, change folder locations, delete or reorder sections, or alter global grouping. Never move a session that is pinned or already assigned to any custom section; keep the user's chosen placement. Use available Desktop sidebar tools: discover `list_sections`, a session listing tool for the current session's pinned and custom-section status, `create_section`, and `move_sessions`. If status cannot be verified, tools are unavailable, or an error occurs, skip filing and continue the task. Find a case-insensitive exact match before creating a section; avoid duplicates. Move only `self` into the section. If the project is still switching at turn end, use the known destination to choose the name but do not file the session if directory access was denied. This organization is best effort; do not claim success without confirmation. Never create a section for one-off tasks.

## Project-specific instructions

For each new project created with the helper, the project folder includes its own `PROJECT.md` for the user's project-specific goals, preferences, and constraints. A separate, minimal `CLAUDE.md` in that same project folder imports it using the unquoted, unescaped `@PROJECT.md` syntax. This is separate from the user's global Claude instructions and does not import sibling projects. Keep `PROJECT.md` short and update it with project-specific instructions the user provides, preserving existing content. Do not invent preferences or copy unrelated information. Do not put secrets in it. If the user asks to change instructions for this project, update its `PROJECT.md`. For an existing project that lacks this setup, only add it when asked or when adding project-specific instructions is appropriate; preserve existing `CLAUDE.md` and `PROJECT.md` content and any existing project conventions, and add the import only if missing. If the project is shared, explain that project files may be shared via version control. Project instructions guide Claude and do not enforce access restrictions.
